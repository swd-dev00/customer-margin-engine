# Migration Strategy & Tooling

## Overview

This directory contains PostgreSQL migration tools and version-controlled DDL for the customer-margin-engine. The strategy emphasizes:

- **Immutability of approved configurations**: Never edit deployed schemas; create new versions.
- **Atomic multi-file deployments**: All slices are versioned together; publish as a unit.
- **Deterministic initialization**: Seed data and test fixtures are reproducible.
- **Rollback safety**: Each migration is reversible; failed runs don't corrupt state.

## Directory Structure

```
migrations/
  bin/
    migrate.sh           # Main migration runner
    rollback.sh          # Rollback runner
    verify.sh            # Verification and consistency checks
  sql/
    000x-*.sql           # Versioned migration files (one per slice or feature)
  fixtures/
    base.sql             # Golden org/customer/project setup
    revenue-sample.sql   # Sample revenue events
    cost-sample.sql      # Sample cost events
  versions.json          # Deployed version state (autogenerated)
```

## Deployment Flow

### 1. New Feature (Slice) Deployment

```bash
# Create migration file
cat > migrations/sql/0009-allocation-results.sql << 'EOF'
-- Slice 9: Shared Cost Allocation Results
CREATE TABLE allocation_rows ( ... );
EOF

# Deploy to dev
./migrations/bin/migrate.sh --env dev --to 0009

# Test
psql $DEV_DATABASE_URL < migrations/fixtures/allocation-test.sql

# Deploy to prod (with advisory lock)
./migrations/bin/migrate.sh --env prod --to 0009 --lock 300
```

### 2. Configuration Change (No schema change)

Configuration changes **do not require migrations**. They are versioned in the `config_versions` table:

```sql
INSERT INTO config_versions (
  organization_id, config_type, version_number, content, fingerprint,
  status, effective_from, approved_by, approved_at
) VALUES (
  $1, 'revenue_mapping', 2, $content::jsonb, $fingerprint,
  'approved', $effective_date, $actor, now()
);
```

## Safety Guardrails

### Advisory Locks

All migrations acquire an advisory lock before modifying schema:

```bash
./migrations/bin/migrate.sh --env prod --lock 300
```

- Prevents concurrent migration runs on the same database.
- Timeout is 300 seconds; adjust for large table operations.
- Failed lock acquisition fails the entire migration.

### Pre-flight Checks

```bash
./migrations/bin/verify.sh --env prod
```

- Validates fingerprints of all deployed schemas.
- Confirms no locked periods have pending calculations.
- Checks for orphaned records.
- Verifies FK constraints are intact.

### Rollback

```bash
./migrations/bin/rollback.sh --env prod --from 0009 --to 0008
```

- Only supported for backward-compatible changes (e.g., adding a nullable column).
- Not supported for destructive operations (e.g., dropping columns).
- Requires explicit approval.

## Migration File Format

Each file must start with a header and include rollback logic:

```sql
-- ============================================================================
-- Migration 0009: Shared Cost Allocation Results (Slice 9)
-- ============================================================================
-- Depends on: 0008 (calculation_runs)
-- Status: forward-only (requires data preservation strategy for rollback)

-- Forward
CREATE TABLE allocation_rows ( ... );

-- Rollback (if supported)
-- DROP TABLE allocation_rows CASCADE;
```

## Testing Migrations

Create a test fixture in `migrations/fixtures/` and run:

```bash
# Load fixture
psql $TEST_DATABASE_URL < migrations/fixtures/allocation-test.sql

# Deploy and verify
./migrations/bin/migrate.sh --env test --to 0009
./migrations/bin/verify.sh --env test

# Run reconciliation test
psql $TEST_DATABASE_URL << 'EOF'
SELECT COUNT(*) FROM allocation_rows WHERE allocated_amount <> 0;
EOF
```

## Deployment Checklist

- [ ] Migration file created with dependency comments.
- [ ] Pre-flight checks pass: `verify.sh --env staging`.
- [ ] Data migration tested in `staging` environment.
- [ ] Rollback plan documented (if applicable).
- [ ] Performance impact assessed (table scans, index maintenance).
- [ ] Advisory lock timeout is appropriate for expected run time.
- [ ] No locked accounting periods block this migration.
- [ ] Approval from platform team obtained.

## Configuration Versioning (No Migration Needed)

For changes to classification, mapping, or allocation rules:

```bash
cat > config-update.sql << 'EOF'
INSERT INTO config_versions (
  organization_id, config_type, version_number, content, fingerprint,
  status, effective_from, approved_by, approved_at
) VALUES (
  $org_id, 'revenue_mapping', $next_version, $content::jsonb, $fingerprint,
  'approved', $date, $actor, now()
);
EOF

psql $DATABASE_URL < config-update.sql
```

New `calculation_run`s will use the latest approved version for their period.

## Monitoring & Alerts

Watch deployment logs:

```bash
tail -f migrations/logs/deployment.log
```

Alert conditions:
- Any failed pre-flight check.
- Advisory lock timeout exceeded.
- Migration runtime > 10 minutes (for initial deploy) or > 2 minutes (for incremental).
- Reconciliation failures after migration.
